# Blueprint: `chenile-process-deployment`

A `chenile-gen` (JGen) blueprint that scaffolds the full
[deployment topology](../deployment.md) from a single spec: one runnable **Process
Manager Server** mini monolith and one or more runnable **Process Manager Worker** mini
monoliths, already wired to each other through a queue and the server's callback URL.

This document is the **blueprint specification**. It is written to live in the
`chenile-gen` repository (`~/Documents/framework/chenile-gen`, `rajakolluru/chenile-gen`)
as a new `bp-process-deployment` module. The runtime repo references it so the deployment
doc and the generator stay in step.

## Where it sits among the existing blueprints

It does not replace the existing `chenile-process-management` blueprint — it composes it:

- **`chenile-process-management`** generates a *single* process application
  (`<app>-api`, `-service`, `-configurations`, `-package`) from a `processSpec`. Use it
  when orchestration and work run in one process.
- **`minimonolith`** generates a runnable Chenile mini monolith with a chosen
  `dependencies[]` set, security, service-registry wiring and `application.yml`.
- **`chenile-process-deployment`** (this one) generates *several* minimonoliths — a
  server and N workers — plus the shared api/config modules, and wires the queue hop and
  `process.manager.base-url` between them. Think of it as `chenile-ecosystem` specialised
  for the process server/worker split.

## Input contract

`jgen -g chenile-process-deployment -o input.json` emits this contract; edit it, then
`jgen -f input.json`.

```json
{
  "application": "orders",
  "applicationVersion": "1.0.0-SNAPSHOT",
  "destFolder": "/path/to/output",

  "definitionSource": "database",
  "transport": "azure",
  "registerInServiceRegistry": false,
  "serviceRegistryUrl": "http://localhost:8080",

  "server": {
    "monolith": "ordersServer",
    "includeProcessUi": true
  },

  "workerPools": [
    {
      "name": "file",
      "monolith": "ordersFileWorker",
      "topic": "orders-file-work",
      "processTypes": ["feed", "file"]
    },
    {
      "name": "chunk",
      "monolith": "ordersChunkWorker",
      "topic": "orders-chunk-work",
      "processTypes": ["chunk"]
    }
  ],

  "processSpec": "three-level-file-processes.json"
}
```

Field notes:

- `definitionSource` — `json` (packaged `def.json`) or `database` (`process_definition`
  table); passed straight through to the server monolith.
- `transport` — `azure` or `kafka`; selects the `chenile-pubsub` dependency and the
  `application.yml` fragment for both publisher (server) and subscriber (workers).
- `server.monolith` — defaults to `${application}Server`. `includeProcessUi` packages the
  admin console behind the management API.
- `workerPools[]` — one entry per worker monolith. `processTypes[]` lists which process
  types that pool performs; the generator cross-references the `processSpec` to emit a
  worker stub (splitter / executor / aggregator, per each type's `leaf`/`children`) for
  each, and sets every one of those types' `config.queue` to the pool's `topic`. This is
  what guarantees the server routes a type to the pool that can serve it.
- `processSpec` — the same spec the `chenile-process-management` blueprint consumes
  (`processes[]` with `processType`, `inputType`, typed `fields`, `children`,
  `implementation`, `config`, `predecessorProcessType`/`predecessorArgs`, and
  `cronTriggers[]`). Reused verbatim so a team can graduate from the single-app blueprint
  to this one without rewriting the spec.

## Generated layout

```
<app>/                                   (enclosing Maven reactor parent POM)
  <app>-api/                             shared model + ProcessDef types (from process-management bp)
  <app>-process-config/                  states XML, def.json or DB seed, cron seeds
  <server-monolith>/                     minimonolith: the brain
  <worker-monolith-per-pool>/            minimonolith: one per workerPools[] entry
  <app>-workers-<pool>/                  worker jars: generated IWorker stubs per pool
```

### `<app>-api` and `<app>-process-config`

Delegated to the existing `chenile-process-management` blueprint's generation of the api
and configuration modules: the model types, the `PROCESS_FLOW` states resource, the
`def.json` (or database seed for `process_definition`) and the `cronTriggers[]` seeds
(seeded disabled). Both monoliths depend on `<app>-api`; the server depends on
`<app>-process-config`.

### Server monolith (a `minimonolith` with a fixed dependency set)

Generated by invoking the `minimonolith` generation with:

```
dependencies = [
  process-service,
  chenile-outbox,
  q-based-process-starter,          # the preferred decoupling starter
  trigger-service, trigger-api,
  crontab-service,
  chenile-pubsub-<transport>,       # publisher side
  <app>-api, <app>-process-config
]
enableH2Console = false
security        = from spec
```

The blueprint's init hook additionally writes the server `application.yml`:

```properties
chenile.process.configurator={{definitionSource}}
chenile.process.outbox.run-dispatcher=true
chenile.process.management.enabled=true
chenile.process.management.api-key=${PROCESS_MANAGEMENT_API_KEY}
spring.datasource.url=jdbc:postgresql://localhost:5432/{{application}}
# chenile-pubsub <transport> publisher connection settings
```

If `server.includeProcessUi` is true it also adds the `process-ui` build and a
same-origin proxy to the management API.

### Worker monolith (one `minimonolith` per pool)

Generated by invoking `minimonolith` once per `workerPools[]` entry with:

```
dependencies = [
  process-delegate,                 # ProcessManagerClient + worker base classes
  chenile-pubsub-<transport>,       # subscriber side
  <app>-api,
  <app>-workers-<pool>             # the generated worker jar(s) for this pool
]
```

The init hook writes, into each worker monolith:

1. A **`ProcessWorkListener`** `@ChenileController` subscribed (`@EventsSubscribedTo`) to
   the worker-dispatch event, taking a `@ChenileBody WorkerDto`, instantiated as a bean so
   the monolith actually registers it. It resolves the `IWorker` for the `WorkerDto`'s
   `workerType`/`processType` and calls `start(workerDto, input)`.
2. A **`chenile-pubsub` subscription** bound to this pool's `topic`.
3. The required **`process.manager.base-url`** in `application.yml`:

```properties
process.manager.base-url=http://{{server.monolith}}:8080
chenile.pubsub.{{transport}}.subscriptions.{{pool.name}}.topic={{pool.topic}}
# no spring.datasource for process state; no outbox poller here
```

### `<app>-workers-<pool>` worker jars

For each `processType` the pool handles, the generator reads the spec and emits a stub
extending the matching base class from `process-delegate`:

- non-leaf type with `children` → a `SplitterBase<Input, ChildInput>` subclass (and, if it
  aggregates, an `AggregatorBase<Input, Output, ChildOutput>` subclass).
- leaf type → an `ExecutorBase<Input, Output>` subclass.

Each stub has a typed `doStart(...)` with a `// TODO` body — the one place the developer
writes domain logic. Everything else (listener, callbacks, queue, base-url) is generated.

## `blueprint.json` sketch

Authored under `bp-process-deployment/src/main/resources/META-INF/blueprint.json`:

```json
{
  "name": "chenile-process-deployment",
  "description": "Server + worker mini-monolith deployment for Chenile process management",
  "templateFolder": "templates",
  "sinceVersion": "2.1.32",
  "inputFields": [
    { "name": "application", "prompt": "Application name" },
    { "name": "applicationVersion", "prompt": "Version", "default": "1.0.0-SNAPSHOT" },
    { "name": "destFolder", "prompt": "Destination folder" },
    { "name": "definitionSource", "prompt": "json or database", "default": "json" },
    { "name": "transport", "prompt": "azure or kafka", "default": "azure" },
    { "name": "processSpec", "prompt": "Path to the process spec JSON" },
    { "name": "registerInServiceRegistry", "prompt": "Register in service registry?", "default": "n" }
  ],
  "initHook": "org.chenile.gen.process.ProcessDeploymentInitHook"
}
```

`server`, `workerPools[]` and the per-pool expansion are not flat prompts; the
`ProcessDeploymentInitHook` reads them from the spec/contract and expands the model the
Mustache templates render against — one server module and N worker modules.

### Template tree (Mustache)

```
templates/
  pom.xml.mustache                                  (reactor parent)
  __app__-api/ ...                                  (delegated / reused)
  __app__-process-config/ ...
  __server__/                                       (server minimonolith templates)
    pom.xml.mustache
    src/main/resources/application.yml.mustache
    src/main/java/__com__/__company__/__org__/.../ServerApplication.java.mustache
  __worker__/                                       (rendered once per pool)
    pom.xml.mustache
    src/main/resources/application.yml.mustache
    src/main/java/.../ProcessWorkListener.java.mustache
    src/main/java/.../WorkerApplication.java.mustache
  __app__-workers/                                  (rendered once per pool, per process type)
    src/main/java/.../%%kind=splitter%%/__Type__Splitter.java.mustache
    src/main/java/.../%%kind=executor%%/__Type__Executor.java.mustache
    src/main/java/.../%%kind=aggregator%%/__Type__Aggregator.java.mustache
```

Path placeholders follow JGen convention (`__app__`, `__App__`, `__com__`/`__company__`/
`__org__`); conditional folders use `%%key=value%%` (e.g. `%%definitionSource=database%%`
for the DB seed, `%%kind=splitter%%` for the worker kind). `sinceVersion` is validated
against the configured `chenileVersion` before any file is written.

## Build and run (generated output)

```bash
jgen -g chenile-process-deployment -o input.json
# edit input.json: name, transport, workerPools, processSpec
jgen -f input.json
cd output/<app> && make build           # mvn install across the reactor

# run the server (needs PostgreSQL + a >= 32-char key)
cd <server-monolith> && PROCESS_MANAGEMENT_API_KEY=<32+ chars> make run

# run each worker, pointed at the server
cd <worker-monolith> && make run        # process.manager.base-url already set
```

## Checklist for implementing the blueprint in `chenile-gen`

- Add `bp-process-deployment` as a blueprint module alongside `bp-process-management` and
  `bp-minimonolith`; register it in the blueprint catalogue.
- Reuse `bp-process-management`'s spec parsing for `<app>-api` / `<app>-process-config`;
  do not fork the `processSpec` schema.
- Implement `ProcessDeploymentInitHook` to (a) expand `workerPools[]` into per-pool
  modules, (b) set each listed process type's `config.queue` to its pool `topic` in the
  generated definitions, (c) classify each process type as splitter/executor/aggregator
  from its `leaf`/`children` to choose the worker stub, and (d) inject
  `process.manager.base-url` into every worker.
- Keep the generated `ProcessWorkListener` in step with the runtime contract: it is a
  `@ChenileController` with an `@EventsSubscribedTo` method taking `@ChenileBody WorkerDto`.
  (The repo currently ships a stub `ProcessWorkListener` in `process-admin-server`; the
  canonical, worker-side version is what this blueprint should emit.)
- Add an example under `bp-process-deployment/examples` (e.g. a two-pool version of
  `three-level-file-processes.json`) so `jgen -g` has a realistic sample.
