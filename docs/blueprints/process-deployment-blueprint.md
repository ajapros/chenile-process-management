# Generating the deployment with JGen

The [server + worker deployment topology](../deployment.md) is **generated by JGen**, not
hand-assembled. This page is the runtime-repo pointer to the generator; the authoritative
guide and templates live in `chenile-gen` (`~/Documents/framework/chenile-gen`).

> **History:** an earlier draft of this page proposed a *new* `chenile-process-deployment`
> blueprint. That is not what shipped. In JGen **2.1.32** the capability landed as a
> **rework of the existing `chenile-process-management` blueprint** plus a new, reusable
> **`chenile-process-workers`** blueprint — composed via JGen's aggregated-blueprint
> mechanism. Use those; there is no separate `chenile-process-deployment` blueprint.

The current maintained source and generator defaults target **Chenile 2.1.33**.
The 2.1.32 labels below describe the blueprint compatibility baseline; the 2.1.33
upgrade is built and tested, with artifact publication pending.

## The two blueprints

- **`chenile-process-management`** (`chenile-gen/jgen/bp-process-management`, since 2.1.32) —
  the deployment generator. From native `processMap` definitions it emits a **process server
  mini-monolith**, a **headless worker mini-monolith**, **per-definition worker JARs**, and
  an **optional service-registry host**, by composing `minimonolith` + `chenile-process-workers`.
  Guide: `bp-process-management/README.md`.
- **`chenile-process-workers`** (`chenile-gen/jgen/bp-process-workers`, since 2.1.32) — one
  plain worker JAR for one process definition: a **leaf** type gets an **executor**; a
  **non-leaf** type gets a **splitter + aggregator** in the same JAR. The `doStart` hooks
  throw until you implement them (they are application code). Reused per-definition by the
  process-management blueprint.

See the **`chenile-jgen`** skill for the full input contracts, the composable
(`super_pom`/`dependencies`) and aggregated (`%{{child}}` marker) mechanisms, and
declarative input validation.

## Input contract (process-management blueprint)

`jgen -g chenile-process-management -o input.json -e` emits the input plus companion sample
spec files; edit them, then `jgen -f input.json`. Key fields:

| Field | Notes |
|---|---|
| `application`, `applicationVersion`, `destFolder` | project identity / output |
| `processSpec` (FILE) | native `processMap` definitions (see below) |
| `cronSpec` (FILE, optional) | **separate** cron schedule array (read by `JsonCrontabRepository`) |
| `definitionSource` | `json` or `database` |
| `registryMode` | `create` (default) or `existing` (+ `existingRegistryUrl`) |
| `registryPlacement` | `server` (recommended) or `separate` (own monolith), when `create` |
| `serverDeploymentUrl` / `workerDeploymentUrl` / `registryDeploymentUrl` | `http://localhost:8000/8001/8002` defaults |
| `transport` | `kafka` (the only supported transport today) |
| `workTopic` | default Kafka topic (`${application}-work`) for any definition lacking `config.queue` |
| `super_pom`, `dependencies` | optional parent POM + extra server-service dependencies |

The process spec keeps the runtime's native shape (not the old `processes[]` array):

```json
{
  "processMap": {
    "Import":    { "leaf": false, "config": { "partitionSize": "100" } },
    "Partition": { "parentProcessType": "Import", "leaf": false },
    "Record":    { "parentProcessType": "Partition", "leaf": true }
  },
  "inputFields": { "Import": { "batchId": "string" }, "Record": { "recordId": "string" } }
}
```

Cron schedules are a separate JSON array (`cronSpec`): `{ name, eventName, cronExpression,
timezone, tenant, enabled, payload: { processDefName, args } }`, seeded **disabled**,
packaged only by the server.

## Generated modules

- `<app>-api` — shared typed payloads + process-start service contracts.
- `<app>-server-config` — native definitions + cron seeds (server only).
- `<app>-server-service` — typed Chenile HTTP services, process bootstrap, runtime services,
  acknowledged Kafka publication (trigger 202/Location). **No** business workers.
- `<app>-<processType>-workers` — one plain JAR per definition (via `chenile-process-workers`).
- `<app>-worker-listener` — headless Chenile Kafka listener: subscribes to every topic,
  validates/restores tenant, invokes workers, calls back through the **registry-backed
  process delegate**, handles retry. No process datasource / process-service / JDBC starter /
  outbox worker.
- `<app>Server`, `<app>Worker` — composed `minimonolith` hosts. The **server uses exactly one
  queue-based (Kafka) starter**; the worker has no process DB.
- `<app>Registry` — only when `registryPlacement=separate`.

How this maps to the topology in [deployment.md](../deployment.md): `<app>Server` is the
**Process Manager Server**; `<app>Worker` + `<app>-worker-listener` + the worker JARs are the
**Process Manager Worker**; the queue hop is Kafka; worker callbacks use
`process.manager.base-url` resolved through the registry.

## Build / run / test

```sh
cd chenile-gen/jgen && mvn install
jgen-cli/bin/jgen.sh -f bp-process-management/examples/file-upload-input.json   # checked-in example
cd output/<app> && mvn install
```

Generated server/worker tests extend `KafkaBaseTest` (Testcontainers) — **Docker must be
running** for `mvn install`; no separately started Kafka is needed. The complete
split/execute/aggregate + remote-callback cycle depends on your worker implementations. The
server initializes the idempotent outbox/receipt SQL schema; Hibernate manages the process,
definition and crontab entities by default.

The stock `process-admin-server` in this runtime repo is **not** the production host — it uses
the in-VM starter and ships no workers. Generate a real deployment with the blueprint above.
